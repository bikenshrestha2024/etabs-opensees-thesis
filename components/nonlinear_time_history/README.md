# Nonlinear Time History

Implementation modules: runner_and_gui.

Load through the matching root compatibility file in MODULE_INDEX_V134.json. See START_HERE.md and VALIDATION_V134.md for data flow and verification scope.

The nonlinear runner keeps UmfPack as its default and allows SparseGeneral or BandGeneral for model-specific timing comparisons. Mumps is not present in the OpenSeesPy 3.8.0 environment checked for this release; no solver is treated as universally fastest. The exploratory building GUI exposes separate gravity and transient choices; SparseGeneral uses pivoting. A full-wall gravity diagnostic with this build terminated the native process when SparseGeneral was selected after the first 0.05 load increment, so treat that path as diagnostic-only and retain UmfPack for normal runs. A failed adaptive gravity solve writes a bounded node/element-response snapshot to `Gravity_Failure_Diagnostics_<limit_state>.json`; this is solver evidence, not an automatic stiffness or connectivity diagnosis. The main program's material sensitivity planner exports a one-factor-at-a-time grade/bar case matrix only; separate model variants, readiness review, and equivalent NLTHA runs are still required.

The exploratory building runner automatically exports `Device_Response_History.csv` for every active FVD/BRB mapping, keyed by solver `device_tag`, at each accepted transient state. It includes axial force, gravity-relative end-to-end displacement, assembly axial velocity, signed cumulative force-displacement work, and the mapped parameters/citation; `Device_Response_Metadata.json` records the definitions and scope. For an FVD, dashpot velocity is inferred from the Maxwell law, `sign(F)*(abs(F)/Cd)^(1/alpha)`, and its integrated force-times-dashpot-velocity is reported separately from total device work. For a BRB, the cumulative value is signed device work, not a standalone cumulative plastic-dissipation claim. These are exploratory recorder outputs: verify device axis, mapped parameter units, element response semantics, and calibration before interpreting device demand or computing design acceptance.

Exploratory FSAM override validation follows the OpenSeesPy documented open intervals `0 < nu < 1.5` and `0 < alfadow < 0.05`; this is command-range validation, not a calibration claim. For transient step sizing, the runner retains NBC §9.3.2.4 limits and adds a separately labelled project safeguard `Tn/10`. The added safeguard is an analyst-imposed numerical rule, not an NBC requirement; it is recorded separately in each exploratory case's `Initial_Modal_Damping.json`.
